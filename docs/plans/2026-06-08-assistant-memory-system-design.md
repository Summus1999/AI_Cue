# 助手模式个人面试记忆系统设计文档

日期：2026-06-08

## 1. 目标

为 AI_Cue 的 assistant 助手模式新增一套个人面试记忆系统，让助手从一次性问答工具，演进为越用越懂用户的实战陪练。系统从用户的真实使用过程中自动沉淀结构化记忆，并在后续答题时按需检索注入，使回答持续贴合用户的项目经历、技术栈、强项与薄弱点。

记忆系统服务于一个明确定位：记住用户在实战助手里遇到的真题和明确表达的意图，而不是再造一个静态文档库。

## 2. 与现有 RAG 知识库的区别

记忆系统和现有 `kb_*` 知识库是互补关系，不是替代关系。两者职责必须分清，避免数据语义混乱。

- 知识库：用户手动导入的静态材料，比如简历、岗位 JD、技术资料。导入即固定，原文切片，服务通用问答。
- 记忆系统：系统从对话、显式指令、复盘录入中自动抽取的动态记忆。可合并、更新、反思、衰减，专属 assistant 模式。

一句话概括：知识库是我准备的材料，记忆系统是我打过的仗的经验。检索时两者都可以注入，但走各自独立的存储和链路。

## 3. 设计边界

### 3.1 本设计包含

- 记忆的分层模型与数据结构
- 三类来源的差异化抽取策略
- 记忆巩固去重、检索打分、反思、衰减的完整生命周期
- 与现有 `EmbeddingProvider`、`chatRetrieval`、review 模块的接入方式
- 分阶段实施拆分

### 3.2 本设计不包含

- 跨设备同步与云端存储
- interviewer 模式下的记忆自动写入
- 多用户隔离（当前产品为单用户本地工具）

## 4. 核心决策

以下决策已与用户确认，作为后续实现的硬约束：

- 服务范围：assistant 模式默认启用记忆检索，interviewer 模式提供开关，默认关闭。
- 抽取时机：实时抽取，每轮助手回答完成后异步触发。
- 记忆来源：assistant 模式遇到的面试题、用户显式指令、事后面试复盘的手动录入。
- 高级能力：反思层与衰减归档都要做。

## 5. 记忆分层

把面试经历拆成四类记忆，各自承担不同职责，不混为一谈。

### 5.1 情景记忆 episodic

一条记忆对应一个具体问答事件。例如某次助手会话里遇到的一道 Redis 持久化题目，以及当时的问答内容。带时间、来源会话、可选的公司与岗位。情景记忆数量最大，是衰减归档的主要对象。

### 5.2 语义记忆 semantic

从多次对话沉淀出的稳定事实。例如用户主导过一个把网关 QPS 从 2000 提升到 12000 的项目。语义记忆是答题时复用的核心弹药。

### 5.3 画像记忆 profile

描述用户长期特征，主要由反思层归纳产生。例如系统设计是反复出现的薄弱点。画像记忆条数少但权重高，常驻注入。

### 5.4 程序记忆 procedural

沉淀出的高质量话术模板，可作为 assistant 模式答题的范例参考。

## 6. 三类来源的差异化处理

三类来源的可信度、结构化程度、抽取方式都不同，必须分别处理。

### 6.1 assistant 模式面试题，实时自动

- 触发点：助手回答流式结束并保存 assistant 消息之后，异步起一个抽取任务。
- 前置闸门：先用廉价判断过滤非面试内容，比如长度、是否疑问句、是否命中技术关键词，命中后才调用 LLM 抽取。这是控制实时抽取成本的关键。
- 产出：情景记忆为主，必要时补充语义记忆。

### 6.2 用户显式指令，实时高优先级

- 识别用户明确表达的记忆意图，比如记住我擅长某项技术、我的项目是某某。
- 采用命令前缀或按钮触发，而非纯意图猜测，避免误判污染正常对话。
- 这类记忆 importance 直接拉满，标记来源为显式指令，豁免自动衰减。

### 6.3 复盘手动录入，手动批量

- 新增录入入口，真实面试结束后由用户填写公司、岗位、题目、回答、结果。
- 结构化程度最高，直接成为高质量语义记忆或画像记忆。

## 7. 记忆生命周期

只存不管理会让记忆膨胀成噪声。完整闭环包含五个环节。

### 7.1 抽取 extraction

用一次 LLM 调用，把来源内容抽成结构化 JSON 记忆候选。复用 review 模块已有的 AI 返回 JSON 再校验的成熟范式，保证抽取结果可控。

### 7.2 巩固 consolidation

新记忆入库前，先做向量检索找高相似度的老记忆。相似度超过阈值就合并更新，累加出现次数并刷新时间，而不是新增。避免同一事实被重复记录。

### 7.3 检索 retrieval

接入现有 `chatRetrieval` 的 sourceKinds 机制，新增一路个人记忆来源。打分参考斯坦福 Generative Agents 的三因子模型：

```
score = α·relevance + β·recency + γ·importance
```

- relevance：查询与记忆的语义相似度。
- recency：按 last_retrieved_at 的指数时间衰减。
- importance：记忆重要性，范围 1 到 10。

assistant 模式默认启用这一路检索，interviewer 模式按开关决定。

### 7.4 反思 reflection

当累计新增 active 记忆达到阈值，触发一次反思任务。让 LLM 读取近期记忆，归纳出更高层的画像记忆。这是系统越用越懂用户的来源。

### 7.5 衰减 decay

情景记忆中 importance 低且长期未被检索命中的，状态改为 archived，不硬删，保留可追溯性。显式指令与复盘录入来源豁免衰减。

## 8. 数据模型

新增两张表，向量表与现有 `kb_embeddings` 同构，便于复用向量化与检索代码。

### 8.1 memories

- id：主键
- memory_type：episodic、semantic、profile、procedural
- source_type：assistant_chat、explicit、manual_review
- content：记忆正文，自然语言，用于注入 prompt
- structured_json：公司、岗位、题目、回答、结果等结构化字段
- importance：1 到 10，显式指令来源固定 10
- embedding_model_id：向量化模型标识
- source_session_id：溯源到来源会话
- occurrence_count：巩固去重时累加
- decay_score：衰减计算缓存值
- status：active、archived
- created_at、last_seen_at、last_retrieved_at

### 8.2 memory_embeddings

- memory_id：外键
- model_id：向量化模型
- vector：向量数据
- dim：维度

## 9. 接入点

优先复用现有设施，新增改动控制在最小集。

### 9.1 复用

- 向量化：直接用 `EmbeddingProvider` trait，支持 qwen 与 openai_compat，无需新依赖。
- 检索注入：扩展 `SearchSourceKind` 与 `chatRetrieval.ts` 的 `getChatRetrievalSourceKinds`，新增个人记忆来源。
- 抽取与反思：复用 review 模块 LLM 出 JSON 再校验的范式。
- 存储：继续 SQLite 本地存储，契合产品的防捕获与本地优先定位。

### 9.2 新增

- 一组 Tauri 命令：记忆抽取、检索、列表、更新、删除、反思。
- 一个记忆管理面板，提供可见、可编辑、可删除的用户控制。

## 10. 分阶段实施

按 Agent.md 一次推进一个子任务的约束，建议顺序如下。

- 阶段 1，后端地基：建 memories 与 memory_embeddings 表、迁移、CRUD 与级联删除，跑通 cargo test。
- 阶段 2，抽取链路：实现 LLM 抽取与 JSON 校验、巩固去重，先做手动录入和显式指令两条确定性来源。
- 阶段 3，实时抽取：assistant 模式每轮异步抽取，加前置闸门与成本、延迟保护。
- 阶段 4，检索注入：扩展 SearchSourceKind 与 chatRetrieval，三因子打分，assistant 默认开、interviewer 开关。
- 阶段 5，反思与衰减：周期反思生成画像记忆，衰减归档低价值情景记忆。
- 阶段 6，记忆管理面板：前端可见、可编辑、可删除的记忆管理界面。

每个阶段都是独立可验证、可提交的子任务。

### 10.1 阶段 1 后端地基用例

- 新数据库初始化后，`user_version` 提升到个人记忆 schema 对应版本，并自动创建 `memories` 与 `memory_embeddings` 表。
- 创建一条 `memory` 时，系统持久化类型、来源、正文、结构化 JSON、重要性、来源会话、出现次数、衰减分、状态与时间字段。
- 查询记忆列表时，默认只返回 `active` 记忆，并按最近更新时间稳定排序；查询单条记忆时返回完整字段。
- 更新记忆时，系统只变更允许编辑的字段，并刷新 `last_seen_at`。
- 删除记忆时，相关 `memory_embeddings` 通过外键级联删除。
- 写入记忆向量时，系统保留 `memory_id`、`model_id`、向量维度和向量二进制数据，并可按记忆删除同步清理。

### 10.2 阶段 2 抽取链路用例

- AI 抽取返回 JSON 或 fenced JSON 时，系统能解析并校验为记忆候选；非法枚举、空内容、空数组或无法解析的 JSON 必须返回明确错误。
- 用户显式指令来源会生成 `semantic` 记忆候选，来源标记为 `explicit`，重要性固定为 10，并保留用户提供的结构化字段。
- 复盘手动录入来源会生成 `episodic` 记忆候选，来源标记为 `manual_review`，并把公司、岗位、题目、回答、结果与备注写入结构化 JSON。
- 记忆候选入库前先生成 embedding，并在同一 embedding model 下查找已有记忆向量；相似度达到阈值时更新已有记忆而不是新增行，同时累加 `occurrence_count`。
- 相似度低于阈值时，系统创建新记忆并写入对应 `memory_embeddings` 记录。

### 10.3 阶段 3 实时抽取用例

- assistant 模式的一轮回答正常完成后，前端以 fire-and-forget 方式触发记忆抽取；抽取任务失败只写日志，不阻塞主回答、消息保存、代码模式检测或 UI 状态更新。
- 非 assistant 模式、回答未完整完成、截图题解、缺少会话 ID、缺少聊天 Provider API Key、缺少 embedding Provider API Key 时，不触发实时抽取。
- 前置闸门会用长度、问号和面试/技术关键词过滤明显无价值内容，避免把寒暄或短句发送给 LLM 抽取。
- 触发实时抽取时，前端把当前会话 ID、用户问题、助手回答、聊天模型配置和 embedding 配置传给后端。
- 后端命令收到请求后复用阶段 2 的 LLM 抽取、候选校验和 embedding 巩固去重链路，并返回抽取候选数和持久化记忆数。

## 11. 风险与权衡

- 实时抽取成本：每轮多一次 LLM 调用会增加 token 消耗和延迟。前置闸门和异步执行是必须的保护手段，抽取任务绝不能阻塞主回答链路。
- 记忆膨胀：没有巩固去重，记忆会快速膨胀并稀释检索质量。巩固环节是阶段 2 的硬性要求。
- 显式指令误判：纯意图猜测容易误记，采用命令或按钮触发更可靠。
- 隐私：记忆包含用户敏感的求职信息，全部本地存储，管理面板必须支持彻底删除。

## 12. 参考做法

- 斯坦福 Generative Agents：Memory Stream 与相关性、时近性、重要性三因子检索，以及反思机制。
- MemGPT 与 Letta：核心常驻上下文与外部按需记忆的分层，以及记忆自我编辑。
- ChatGPT 与 Claude Memory：区分显式保存记忆与隐式提取记忆，并交还用户可见可控的管理权。
- 认知科学记忆类型学：情景、语义、程序记忆的分类骨架。
